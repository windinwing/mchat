# 方案 A：建立纯净 Core 分支（单仓多分支）

## 核心策略：减法而非加法

**不从 main/dev 往上叠 commit，而是从 `feature/channel-rental`（含全部最新代码）做减法——删掉 cloud，剩下的就是最新 Core。**

理由（调研结论）：
- `feature/channel-rental` HEAD 已包含全部 104 个 commit 的 Core 改动（无需 cherry-pick 92 个 commit）
- 后端 `from cloud.*` 的 import **全部已被 `try/except` 包裹**——删掉 `cloud/` 目录后 `app.main` **零改动即可启动**
- `subscription_gate` 和 `field_encryption` 在 Core 单租户下**已经是 pass-through 安全的**（free plan → gate 返回 active；无 key → 明文存取），无需 stub
- dev 独有的 10 个 commit 里，6 个已在 feature 分支（不同 hash），ComfyUI 编辑器也已包含且更完整，**只剩 2 个有价值**（migration 列 + toast 修复），需验证是否已在 feature 中

**代价**：git 历史里会保留 cloud 开发记录（commit 存在但文件在清理 commit 中删除）。对开源仓库可接受——发布时 force-push 为新 main，或保留"移除 cloud"的清理 commit。

## Phase 3：发布到 GitHub

当前 `origin/main` = `dev`（40f0d08，污染）。两种发布方式：

**推荐：force-push（干净）**
```
# 先备份当前 main
git tag backup-origin-main origin/main
git push origin backup-origin-main
# 推送 core 为新 main
git push origin core:main --force
```
> 风险：重写 GitHub 历史。但这是个人仓库（windinwing/mchat），且当前 main 本身就是错误状态。

**备选：保留历史（在 dev 上叠加删除 commit）**
> 不推荐——会在污染的 dev 基础上工作，且无法带入 feature 的 104 个 commit。

## Phase 4：建立长期工作流（单仓多分支）

```
core 分支 (GitHub origin/main)          feature/channel-rental (private remote)
    │                                          │
    │  Core 修复/功能                           │  Cloud 专属功能
    │                                          │
    └──────── merge core ──────────────────────►│  (Cloud 继承 Core 改动)
                   │
                   │  永远不反向 merge
                   │  永远不 push cloud 文件到 origin
```

**规则（与 `docs/core-cloud-split.zh.md` 一致）：**
1. Core 修复先进 `core` → push `origin main`
2. 定期 `git merge core` 进 `feature/channel-rental`（Cloud 继承 Core）
3. **永远不**把 `feature/channel-rental` merge 回 `core`
4. Cloud 专属改动只留在 `feature/channel-rental` → push `private`

**可选防护：** 在 `core` 分支加 pre-push hook，阻止 `cloud/`、`portal/` 文件被推送：
```bash
# .git/hooks/pre-push (core 分支)
git diff --name-only HEAD | grep -E "^src/backend/cloud/|pages/portal/" && {
  echo "BLOCKED: cloud files must not enter core branch"; exit 1
}
```
