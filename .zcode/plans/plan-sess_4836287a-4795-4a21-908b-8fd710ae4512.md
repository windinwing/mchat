# 修复三个问题：Cloud 登录显示、刷新空白页、admin/agent 共享 AI 配置

## 问题 2（刷新空白页）— 根因修复：auth store 初始状态

**根因**：`src/frontend/src/stores/auth.ts:39-40` 把 `isAuthenticated` 同步初始化为 `!!localStorage.getItem('mchat_token')`（token 在就为 true），`isLoading: false`。token 过期后刷新，`isAuthenticated` 暂时为 true、`isLoading` 为 false，各路由守卫不拦截 → 子组件挂载发请求 → 401 → 组件渲染 `null` + `api.ts` 硬跳转竞争 → 白屏。`AdminLayout` 已用本地 `authChecked` 绕过（`AdminLayout.tsx:33-46`），但 `UserLayout`/`ChatHomePage`/`ChatPage` 没修。

**修复（一处根因）**：`auth.ts`——当 token 存在时，初始 `isLoading: true`。这样刷新后首次渲染就被 loading 拦住，直到 `checkAuth()` 返回；token 有效才渲染子组件，token 无效则各守卫跳登录。这是 `AdminLayout` 那段注释描述的正确做法，统一到 store 层。

```ts
// auth.ts 初始化
const hasToken = !!localStorage.getItem('mchat_token')
isAuthenticated: hasToken,   // 仍乐观为 true（避免已登录用户闪烁）
isLoading: hasToken,         // 关键：有 token 时初始 loading，等 checkAuth 验证
```
同时 `checkAuth()` 在无 token 分支保持 `isLoading: false`（已正确）。

这样 `UserLayout.tsx:62`、`ChatHomePage.tsx:242`、`ChatHomePage.tsx:145`、`useAuth.ts:14` 全部受益，无需逐个加 `authChecked`。`AdminLayout` 的 `authChecked` 保留（不冲突，多余但无害）。

**额外加固 `ChatPage`**：`ChatPage.tsx` 目前完全没有 auth 守卫（路由 `routes.tsx:134` 裸挂载）。加一个最小守卫：`checkAuth()` + 未认证跳 `/admin/login`，用 store 初始 `isLoading` 拦住首次渲染。

## 问题 1（登录/注册在 10.98.8.15 没显示）— 运行时读后端 + 修部署脚本

**根因**：`isCloudEdition`/`isSignupEnabled`（`edition.ts`）是**构建期** `VITE_MCHAT_EDITION` flag，和后端解耦。部署用错脚本（core 构建）就没了注册 UI，即使后端是 cloud。

### 1a. 后端：扩展 `/auth/bootstrap` 返回 features
`src/backend/app/schemas/auth.py` 的 `BootstrapResponse` 加字段；`src/backend/app/api/auth.py` 的 `bootstrap_hint()` 填充：
```python
class BootstrapResponse(BaseModel):
    username: str
    password: str | None = None
    show_credentials: bool = False
    signup_enabled: bool = False      # 新增
    cloud_edition: bool = False       # 新增（cloud.main 是否在跑）

# auth.py bootstrap_hint()
return BootstrapResponse(
    username=..., password=...,
    show_credentials=show,
    signup_enabled=settings.signup_enabled,
    cloud_edition=settings.is_cloud_edition,  # 新增 config 字段
)
```
`config.py` 加 `is_cloud_edition` 计算属性：cloud.main import 成功则为 True（或用 `RUNNING_CLOUD` 环境变量；最简：cloud/main.py 启动时 `settings.cloud_mode = True`，Core 不设）。实现：在 `app/core/config.py` 加 `mchat_cloud_mode: bool = False`，在 `cloud/main.py:create_core_app` 包装处设为 True（或 cloud app 启动前 set）。

> 注：`bootstrap` 是公开接口（无 auth），LoginForm 启动时已调用它（`LoginForm.tsx:59`），零额外请求。

### 1b. 前端：`edition.ts` 运行时与构建期取并集
保留构建期 `isCloudEdition`/`isSignupEnabled` 作为**默认/首屏**（避免阻塞首屏），新增运行时覆盖：
```ts
// edition.ts
export const isCloudEdition = import.meta.env.VITE_MCHAT_EDITION === 'cloud'
export const isSignupEnabled = isCloudEdition || import.meta.env.VITE_MCHAT_SIGNUP_ENABLED === 'true'

// 新增：运行时从后端拉取，宽松化（后端开了就开）
let runtimeOverride: { cloud?: boolean; signup?: boolean } | null = null
export function setEditionRuntimeFlags(f: { cloud?: boolean; signup?: boolean }) {
  runtimeOverride = f
}
export function getEditionEffective() {
  return {
    cloud: isCloudEdition || !!runtimeOverride?.cloud,
    signup: isSignupEnabled || !!runtimeOverride?.signup,
  }
}
```
`LoginForm.tsx` 的 bootstrap 请求里调 `setEditionRuntimeFlags({ cloud: data.cloud_edition, signup: data.signup_enabled })`，并用 `getEditionEffective()` 替代直接读 `isSignupEnabled`/`isCloudEdition`（仅 LoginForm 的 `portalLogin` 判断，决定显示注册/手机/9235）。

**LandingPage.tsx**：首屏用构建期 flag（不变）；登录后/刷新到 landing 时 bootstrap 已加载，可读 effective。改动聚焦 LoginForm（注册入口所在）。

### 1c. 修部署脚本/文档
- `ops/scripts/deploy-remote-cloud.sh`：确认 `VITE_MCHAT_EDITION=cloud`（已正确）。
- 核查 10.98.8.15 实际跑的是 `mchat-cloud-backend.service`（`remote-setup-cloud.sh` 会停掉 core 的 `mchat-backend.service`）。
- 在 `gamecenter-server.env.example` 顶部加注释说明 10.98.8.15 = cloud，必须用 `make deploy-cloud`。
- **有了 1a/1b 后**，即便前端误构建成 core，只要后端 `signup_enabled`/cloud 为真，登录页也会自动显示注册——彻底消除"搞混"。

## 问题 3（admin/agent 共享系统 AI 配置，列表可见）— 完整共享

用户选「完整共享 + 列表可见」：admin 创建的 `is_default=True` 配置即"系统配置"，所有 admin/agent 可用且在工作台可见（只读标识），setup 不再卡。

### 3a. 后端 setup_status：admin/agent 都按全局默认判 `ai_ready`
`src/backend/app/services/setup_status_service.py:77-80` 当前 agent 被 `where(user_id==self)` 限制。改为：**admin 和 agent 都查全局**（和运行时 `handler.py:104` 一致）。
```python
# 删除 is_admin 分支，admin/agent 一律全局查（role=="user" 已早返回）
ai_query = select(AIConfig).where(AIConfig.is_default == True)  # 或全量
```
`_ai_configs_ready` 已存在，逻辑不变。`ai_config_count` 改为反映用户**可见**配置数（见 3b）。

### 3b. 后端 `/agents/ai-configs`：返回「自己的 + 全局默认」
`agent_service.py` 的 `list_ai_configs(user_id)`：保留现有自建列表，再 union 全局 `is_default=True` 的非本人配置，标记 `shared=True`。在 `AIConfigResponse`（`schemas/agent.py`）加 `shared: bool = False`（默认 False，向后兼容）。

**关键约束**：
- `get_ai_config`/`update_ai_config`/`delete_ai_config` 对 shared 配置**只读**（非 owner 不能改/删）：在这些方法里若 config 不属于该 user 且 `is_default`，get 放行、update/delete 返回 None/False（API 层 403/404）。
- 这样 shared 配置能在工作台"查看/选用"（测试连接、拉模型列表用其 api_key），但不能被非 owner 改坏。

### 3c. 前端工作台：显示 shared 配置 + 系统默认标识
`ModelProviderWorkbench.tsx`：
- `AIConfig` 接口加 `shared?: boolean`。
- 列表渲染（`~line 360-377`）：shared 配置名后加「系统默认」徽章（复用 `workbenchDefaultBadge` 样式或新增 `workbenchSharedBadge`），保存按钮对 shared 禁用（只读提示）。
- 空状态文案（`workbenchEmptyConnections`）仅在"既无自建又无 shared"时显示。

`AgentConfig.tsx`：同样加 `shared?: boolean`，shared 时不允许改 prompt（禁用保存）。

### 3d. i18n 新增 key
en.json / zh.json 的 `agents` 下加：
- `workbenchSharedBadge`: "System default" / "系统默认"
- `workbenchSharedReadOnly`: "Shared system config (read-only)" / "共享系统配置（只读）"
