# 群组协作 MVP 方案

> 目标：在尽可能不增加复杂度的前提下，为 MChat 增加群组、共享记忆、共享知识库能力，并兼容 Core/Dev 与 Cloud 两条产品线。

## 1. 核心原则

### 1.1 群组不是新主体

群组不是新用户、不是新租户、不是新的执行工作区，只是一个协作作用域。

系统中三层职责保持不变：

- 用户：登录主体、个人资料、个人工作区
- 角色：权限控制
- 资产：Skill、知识库、工作流、模板、频道

群组只负责“团队共享上下文与默认资产”。

### 1.2 内部只保留一个聊天入口

内部用户继续使用 `/chat`。

群组不是新的聊天产品入口，而是 `/chat` 内的作用域切换：

- 个人空间
- 群组 A
- 群组 B

### 1.3 不做群组级 sidecar

执行工作区仍保持每用户一套：`skills/`、`uploads/`、`data/`。

群组只共享：

- 群组知识库
- 群组记忆卡片
- 群组默认 Skill 集
- 群组模板

群组不共享：

- sidecar
- 用户私有执行目录
- 用户个人会话列表

### 1.4 先共享上下文，不共享实时会话

MVP 不做多人共用同一会话线程。

MVP 只做：

- 同群组成员都能使用同一套群组知识和记忆
- 每个人的对话仍归个人名下

这样能避免未读、会话转交、并发编辑、消息归属等复杂度。

## 2. Core / Dev 与 Cloud 的统一策略

### 2.1 后端能力必须放在 Core

群组相关核心逻辑应放在：

- `src/backend/app/models/`
- `src/backend/app/services/`
- `src/backend/app/api/`

不要只放到 `src/backend/cloud/`。

原因：

- Core/Dev 也有内部团队协作需求
- Cloud 只是多了一层门户、模板市场、计费
- 群组是协作域，不是 SaaS 专属能力

### 2.2 Cloud 只增加薄入口层

Cloud 与 Core 共享：

- 数据模型
- 权限规则
- 聊天作用域
- 群组知识库与群组记忆逻辑

Cloud 额外增加：

- 门户里的群组展示页
- 门户里的群组知识库维护入口
- 套餐/成员数/知识库数量限制

不要让 Cloud 再维护一套独立的群组后端模型。

### 2.3 Dev 先从后台和 `/chat` 做起

Dev / Self-host 推荐先只提供：

- `/admin/groups`
- `/chat` 作用域切换

先不急着做完整门户群组页，这样能先把领域模型和权限跑通。

## 3. 群组与角色、用户的分工

建议职责固定：

- 角色：决定“能不能做”
- 群组：决定“团队默认用什么”
- 用户：决定“我个人额外加什么”

推荐优先级：

1. 角色检查权限
2. 群组提供默认资产
3. 用户追加个人私有资产

不要让角色继续承担主要的团队协作配置。

## 4. 群组共享知识库

### 4.1 为什么应该先做它

共享知识库比共享 Skill 更适合团队协作，因为它：

- 支持多人维护
- 能直接参与 RAG 检索
- 不进入执行容器
- 不引入代码执行风险

### 4.2 最低复杂度数据模型

建议在现有知识库模型上做最小扩展，而不是重做一套群组 RAG。

推荐做法：

- 保留 `knowledge_bases.user_id` 作为创建人或归档责任人
- 新增可空字段 `group_id`

语义变成：

- `group_id is null`：个人知识库
- `group_id is not null`：群组知识库

这样可以复用现有文档、切块、索引、检索链路。

### 4.3 存储与执行边界

群组知识库仍属于控制面资产，不下沉到用户 sidecar。

也就是说：

- 文档导入、向量化、检索仍走控制面
- sidecar 继续只做用户 Skill 执行

### 4.4 MVP 使用方式

MVP 先做两种用法：

1. 群组聊天时默认启用群组知识库
2. 后台中可维护群组知识库文档

## 5. 群组共享记忆

### 5.1 第一版不要做成公共 Skill

共享记忆第一版应该是结构化记忆卡片，而不是可执行 Skill。

推荐类型：

- `prompt`
- `playbook`
- `faq`
- `decision`
- `example`

每条记忆至少包含：

- 标题
- 内容
- 标签
- 适用方向
- 创建人
- 最后编辑人
- 更新时间
- 是否已验证

### 5.2 运行时怎么用

当用户在 `/chat` 选择某个群组作用域时：

1. 先检索群组记忆卡片
2. 再检索群组知识库
3. 将命中结果拼接进 system prompt

### 5.3 必须保留版本历史

共享记忆若没有版本历史，很快会变成脏数据。

MVP 至少应支持：

- 当前版本
- 修订记录
- 简单回滚

## 6. 推荐 MVP 数据模型

建议新增：

- `groups`
- `group_members`
- `group_memory_entries`
- `group_memory_revisions`

建议最小扩展：

- `knowledge_bases.group_id nullable`
- `conversations.scope_type`
- `conversations.scope_id`

群组默认 Skill 第一版可直接挂到 `groups.default_skill_ids` JSON 字段。

## 7. MVP 权限规则

群组成员角色先只做三档：

- `owner`
- `editor`
- `member`

对应能力：

- `owner`：成员管理、群组设置、删除群组
- `editor`：维护群组知识库、编辑群组记忆、调整默认 Skill
- `member`：使用群组聊天、查看共享知识与记忆

## 8. 明确不做什么

MVP 不做：

- 群组级 sidecar
- 群组独立租户目录
- 群组共享实时会话
- 群组独立登录入口
- 群组级代码执行空间
- 复杂审批流

## 9. 推荐实施顺序

### Phase A：先打底

- 新增群组与成员模型
- `/chat` 增加作用域切换
- conversations 支持 scope 字段

### Phase B：做共享知识

- `knowledge_bases.group_id`
- 群组知识库列表 / 新建 / 上传文档
- 群组聊天纳入群组知识检索

### Phase C：做共享记忆

- 记忆卡片 CRUD
- 版本历史
- 聊天检索注入

## 10. 最终建议

如果目标是“尽可能不增加复杂度”，就坚持三条：

1. 群组是作用域，不是新身份
2. 内部只有一个聊天入口，不新增群组聊天产品
3. 群组先共享知识和记忆，不共享执行容器和实时会话

按这个路线推进，Core/Dev 和 Cloud 都能共用一套后端逻辑，Cloud 只增加展示层和套餐限制，复杂度会明显可控。
